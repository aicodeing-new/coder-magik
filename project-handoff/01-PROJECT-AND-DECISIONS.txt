项目目标和已确认决策

项目：aicodeing-new/coder-magik，源自Coder，工作目录/root/coder。
源码目标仓库：https://github.com/aicodeing-new/coder-magik。
产品用途：公司内部GPU研发平台，研发只优化LLM推理引擎，包括vLLM/SGLang二开和EP测试，不涉及训练。
希望集中管理多个GPU集群、通过VS Code/Desktop/SSH使用环境、保存开发数据、可停机释放GPU并再次启动继续开发。
用户宣布当前是初版成功上线，后续以稳定运维和迭代为主。

用户明确确认的环境策略
- GPU开发Pod参照线上推理Pod配置，初期整机8GPU，避免和线上任务占用同一批GPU。
- 后续明确要求研发创建时可选0至8GPU，已实现，默认8。
- 开发Pod privileged=true、root、hostNetwork=true，不开hostPID/hostIPC。
- 不设置CPU和内存的Pod requests/limits；共享节点硬件，不等于严格安全隔离。
- 每个工作空间独立PVC，不挂主机/data或模型目录。
- GPU通过Kubernetes requests/limits预约；privileged和主机socket意味着不能承诺跨研发人员硬件/宿主机权限隔离。
- 不通过调度抢占、解除节点限制、绕过GPU分配解决资源等待。
- 用户要求Docker管理主机已有容器，选择挂主机运行时socket；不是每个空间启动独立dockerd。
- 不同集群使用不同代理，Pod环境变量配置必须进入模板，避免重建后丢失。
- GPU没有公网访问；用户最后明确只有三台CPU服务器能上网。具体其他两台CPU身份未提供。

多集群
单个Coder控制面可通过多个受限kubeconfig context管理多个GPU集群，不需每集群重复部署Coder。
单个kubernetes模板允许创建时选择beast01/yunqiao；工作空间创建后不改集群，数据不自动跨集群迁移。
更换集群通常新建空间并显式迁移数据；不能把现有PVC当成跨集群共享卷。
0GPU不预约GPU、不使用nvidia RuntimeClass，设置NVIDIA_VISIBLE_DEVICES=void；不保证调度到CPU节点。
先前CPU节点都不可正常调度，0GPU空间仍可能落在GPU节点。

数据和命名
PVC名称：coder-<workspace UUID>-home；Deployment：coder-<workspace UUID>。
Pod名称是Deployment生成的ReplicaSet/hash后缀，不固定为用户填写的名字。
workspace名字、owner、UUID等保存在Kubernetes标签，可关联平台对象。
停止空间：删除开发Deployment/Pod，保留PVC；重新启动时挂原PVC，节点可能变化。
删除整个空间：Terraform删除PVC；当时集群PV reclaimPolicy=Retain，底层数据需单独处理，不等于立即销毁。
确认删除后的数据管理必须重新检查实际PV策略，不能仅凭历史记录作决定。
持久化范围/home/coder；rootfs中的apt包、/tmp、默认/root目录、未放入PVC的依赖不随Pod重建保留。
新空间默认100Gi；zy-test-1保留历史10Gi；当前yunqiao测试空间实际50Gi。
两个GPU集群使用ceph-fs，开发/home按RWO申请，不主动共享工作目录。

自定义开发镜像
已实现创建表单填写完整image tag或digest，后续修改参数并重建Pod。
admin Terraform var dev_image提供默认，实际容器使用coder_parameter.dev_image。
默认swr.cn-north-4.myhuaweicloud.com/pixiu-public/admins/example-base:ubuntu。
研发二开vLLM/SGLang镜像尚未制作，公司自己的基础镜像可使用，但必须符合启动契约。
镜像至少sh/bash/curl或wget；Codex插件预装还需tar、grep，Docker主机管理需Docker CLI/ctr。
平台覆盖镜像ENTRYPOINT，推理服务需用户启动或通过Agent脚本启动。
避免预装文件只放/home/coder，否则PVC挂载会遮住镜像原内容。优先放/opt并初始化复制所需文件到PVC。
私有镜像pull权限在每个GPU集群配置；Pod的HTTP_PROXY不替代节点containerd拉取镜像的网络配置。
更换镜像保留PVC，但可能改变Python/CUDA/依赖兼容性，需要实际验证。

VS Code和Desktop
VS Code Remote SSH Server/扩展安装在/home/coder/.vscode-server，随PVC持久化。
如果不同镜像HOME改回/root则不能沿用此结论；当前模板固定HOME=/home/coder。
本地Windows扩展、Coder插件和Remote SSH配置属于研发人员电脑，不在工作空间PVC里。
Desktop可通过Coder连接工作空间网络，辅助本机IDE/SSH/端口访问；不把GPU变成本机CUDA设备，也不自动迁移数据或镜像。
当前Desktop已由用户确认能连接，未全面验证每项Desktop功能。
Codex VS Code扩展预装完成，但不预置研发人员的OpenAI登录/API凭据，首次需用户自行登录。

账号与创建权限
飞书OIDC允许注册，默认活跃用户进入默认组织；模板Everyone组具有Use权限。
因此当时所有在该组织注册并活跃的人员都能使用模板创建空间，仍受实际RBAC、模板ACL和资源限制。
飞书应用可用人员范围在飞书侧控制；仅能登录不等于永久具有所有模板管理权限。
已有SuanFa组包含两位用户，当时未把模板改成仅该组可用。
尚未实施研发组白名单、配额和更细粒度资源隔离。

多机EP测试
hostNetwork使Pod可通过节点内网IP互联，程序端口不得和同节点服务冲突。
当前模板只创建单个Deployment副本，没有自动多机参数、headless Service、每空间固定DNS或分布式启动编排。
Kubernetes Pod名不自动成为可用于跨Pod访问的稳定DNS记录。
需要稳定DNS时应新增Service/headless Service等并扩展当前受限RBAC；这部分尚未实现。
EP需分别预约所需GPU节点，并验证IB/RDMA、NCCL、端口、拓扑、驱动和两端软件版本；此前未执行多机EP测试。
